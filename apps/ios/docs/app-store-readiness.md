## 4.2: ネイティブ版としての実用性

Appleは、Webサイトの再包装を超える機能・UIと十分な実用性を求めています。[App Review Guidelines 4.2](https://developer.apple.com/app-store/review/guidelines/#minimum-functionality)

以下は本プロジェクトで示す実用性の候補であり、Appleが列挙する必須機能の転載ではありません。

- [ ] ネイティブ画面で教材の作成・編集・検索・再表示ができる。WebViewの入口だけで終わらない。
- [ ] 再起動・バックグラウンド復帰後の保存状態、保存失敗時の入力保持を確認する。
- [ ] 文書選択・プレビュー・書き出し／OS共有のうち、初版で提供する操作を明確にする。共有はユーザーが選んだファイルだけを対象にする。
- [ ] 共通coreの入力制限・ファイル容量上限・エラー表現を定め、クラウド同期やチーム権限があるかのようなダミー画面を出さない。
- [ ] 飛行機モード等で使える範囲と、ネット接続が必要な操作を画面・説明で一致させる。
- [ ] PDF/PPTX等は、実在するファイルを開いて確認する。「編集可能」のフラグだけを機能の証拠にしない。
- [ ] 小さいiPhone、文字拡大、VoiceOver、ライト／ダーク表示、キーボード表示中の操作を確認し、架空データの証拠を残す。

## アカウント: 5.1.1(v)と4.8の分岐

アカウント作成を提供するアプリでは、アプリ内から削除を開始できる必要があります。停止・無効化だけでは足りず、通常のアプリで電話・メール等の問い合わせを削除の必須経路にすることも避けます。[Apple: Offering account deletion](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion)

既存Web版の[保存・運用上の残件](../../marketplace/README.md)にはアカウント削除や所有権移管の未実装が含まれます。Webの保管庫が動くことだけで、クラウド版iOSの提出準備が完了したとは判断しません。

- [ ] **クラウド版を選ぶ場合**: アカウント画面に削除開始・確認・完了／処理中表示を実装し、本人確認を含めた正常系・取消・失敗系を検証する。Web登録へのリンクだけにして削除を省略しない。
- [ ] 削除対象を、アカウント、個人教材、添付、端末キャッシュ、セッション、共有・招待の関係で定義する。保持する情報・期間・理由があれば説明する。
- [ ] チーム所有者が削除する場合の、所有権移管またはチーム削除の扱いを本人と決める。別メンバーの教材を黙って削除しない。
- [ ] 削除後の再ログイン拒否、端末キャッシュ消去、共有／招待失効を確認する。バックアップ復旧で削除済みアカウントが復活しない運用も定める。
- [ ] 削除に時間が必要なら所要時間・完了通知を説明する。取得済みの他端末ファイルを遠隔削除できると案内しない。
- [ ] **端末内版を選ぶ場合**: サービスアカウントを作成しない設計であることを確認し、不要なID／パスワード画面を置かない。端末データの全消去・書き出し・バックアップの説明は別に用意する。

  4.8には、独自の登録・ログインのみを使用する場合の追加ログイン免除があります。独自IDだから直ちにSign in with Appleが必須、とは扱いません。第三者／ソーシャルログインを追加する際は、同条の同等ログイン要件を再評価します。[App Review Guidelines 4.8](https://developer.apple.com/app-store/review/guidelines/#login-services)

- [ ] 初版のログイン方式と、4.8の適用／免除理由を審査メモに残す。
- [ ] Google等のログインを追加する変更を、この免除のまま進めない。Sign in with Appleを採用した場合は、削除時のトークン失効も検証する。

## 5.1: プライバシーとデータの実態

プライバシーポリシーはApp Store Connectとアプリ内から参照できる形で用意し、収集・利用・共有・保持／削除の実態を説明します。[App Review Guidelines 5.1](https://developer.apple.com/app-store/review/guidelines/#privacy)

- [ ] クラウド／端末内の選択後、ID、教材本文、添付、ログ、診断情報、外部SDK、バックアップの保存先・送信先・保持期間を表にする。
- [ ] 個人プロジェクトの有効なHTTPSプライバシーURLを用意する。雛形だけ、存在しないURL、業務環境のURLを設定しない。
- [ ] App Privacy回答を実ビルドの通信・SDKと照合する。「ローカル版」という名称だけで「収集なし」と回答しない。App Privacyは第三者SDKの収集も対象です。[App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/)
- [ ] 権利確認を外部AIへ送信する機能は、無断で追加しない。現状のローカル文字検査・画像／OCR未検査の説明を実装と揃える。
- [ ] ファイル選択、写真等の権限は初版で必要なものに限定する。拒否された場合の操作を確認し、不要な連絡先・位置・マイク権限を求めない。
- [ ] 採用API／SDKに応じてPrivacy Manifestとrequired-reason APIの申告を確認する。ファイルの存在だけで申告完了としない。[Privacy manifest files](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files)
- [ ] 実利用者の氏名、診断名、支援記録、業務資料をfixture、スクリーンショット、ログ、CI artifactへ入れない。教材補助アプリを診断・治療・効果保証として説明しない。

## 1.2: 投稿・チーム共有を提供する場合

AppleのUGC要件は、不適切な内容のフィルタ、通報と対応、悪用ユーザーの遮断、連絡先の公開を含みます。[App Review Guidelines 1.2](https://developer.apple.com/app-store/review/guidelines/#user-generated-content)

- [ ] **クラウド／チームで他者の教材を扱う版**: 上記4項目を、アプリ内導線と運営手順に対応付ける。著作権の注意表示だけでUGC対応済みにしない。
- [ ] 通報先、受付担当、対応・停止・再審査の流れを決め、架空の教材で通報から失効まで確認する。
- [ ] 管理者によるチーム除外と、サービスとしての悪用ユーザー遮断を区別する。通報者が再度その内容に曝されない動作を確認する。
- [ ] 限定リンクが転送された場合の停止経路を用意する。宛先固定のチーム招待と、閲覧者を固定しない共有リンクを混同しない。
- [ ] **端末内版**: アプリ内のユーザー間投稿・他者教材閲覧サービスを提供しない範囲を文書化する。OSのファイル書き出しの挙動も説明する。「限定共有だから1.2免除」と断定しない。
- [ ] 教材の権利根拠と相談窓口を示す。自動アラートは法的許諾や審査通過の保証として表示しない。

## 提出物と審査アクセス

- [ ] アプリ名、Bundle ID、カテゴリ、対象年齢、配布地域、バージョンを本人が確定する。個人プロジェクトの権利者表示と、アソシアとの分離を確認する。
- [ ] スクリーンショットは完成したネイティブ画面から架空データで取得する。未実装のクラウド・チーム機能を掲載しない。必要表示サイズ・形式は提出時に[Appleのスクリーンショット仕様](https://developer.apple.com/help/app-store-connect/reference/app-information/screenshot-specifications)と照合する。
- [ ] 有効な個人プロジェクトのSupport URLと連絡手段、説明文、著作権表記、実態と一致するレビュー情報を揃える。[Platform version information](https://developer.apple.com/help/app-store-connect/reference/app-information/platform-version-information)
- [ ] クラウド版は審査用の架空アカウントと必要な手順を準備し、審査中のバックエンドを利用可能にする。実際のユーザーや業務アカウントを渡さない。
- [ ] 端末内版は、初回起動から教材作成・保存・検索・削除を審査者が再現できるようにする。
- [ ] 審査メモに保存方式、ネット接続範囲、権利検査の限界、アカウント削除／UGCの適用範囲を記載する。秘密鍵や通常開発用の資格情報はリポジトリへ入れない。

## Mac CI、署名、TestFlightの区別

| 段階                                  | 合格として残す証拠                                                         | この段階だけでは確認できないこと             |
| ------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------- |
| ネイティブ共通coreの単体検証          | 小さい架空fixture、正常・拒否系、実行結果                                  | iOS画面、実機、署名、審査                    |
| Mac CIの署名なしbuild／Simulator test | 実際のrunner、Xcode／SDK、終了結果、テスト件数、必要な画面証拠             | 署名付き配布、実機権限、TestFlight利用可能性 |
| 個人用MacとiPhoneでの検証             | 対象端末／OS、起動・保存・復帰・ファイル操作・権限拒否の結果               | 外部配布やApp Reviewの承認                   |
| 署名付きarchive／配布検証             | 本人が選んだTeam／Bundle ID、署名・profile、export compliance、検証結果    | TestFlight外部テスト承認、一般公開           |
| TestFlight                            | App Store Connectで処理されたbuild、テスト情報、必要なベータ審査、実機結果 | App Store本審査の合格                        |

- [ ] Mac CIは**予定**と**実行済み**を分けて記録する。Linux上のテスト成功をXcodeビルド成功と表現しない。
- [ ] Xcode／SDKの提出要件を[Upcoming Requirements](https://developer.apple.com/news/upcoming-requirements/)で提出時に確認する。確認時点ではXcode 26以降・iOS 26 SDK以降のアップロード要件が示されています。deployment targetの選択とは別です。
- [ ] 個人用Developer ProgramのTeamとApp IDを本人が選ぶ。配布profile等を用意する段階で、署名なしの成果物から区別する。[App Store provisioning profile](https://developer.apple.com/help/account/provisioning-profiles/create-an-app-store-provisioning-profile/)
- [ ] TestFlightへ進む前に署名、アップロード、暗号化／輸出関連の回答とテスト情報を確認する。外部テストにはベータ審査が必要になるため、招待済みと利用可能を区別する。[TestFlight overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/)
- [ ] 招待や外部配布は本人の判断後に行う。CIで自動upload・自動公開する設定を、開発承認だけで有効にしない。

| ゲート                      | 本人が確認・承認すること                                                    | 未決なら進めない操作                       |

| G2 共有・データ運用         | 削除・UGC・プライバシー・サポートの実装と運営責任                           | クラウド／チーム機能の外部提供             |
| G3 署名とTestFlight         | Team／Bundle ID、秘密情報の保管、build、テスト相手、配布範囲                | 証明書・キーの発行、upload、外部招待       |
| G4 販売する場合の契約       | 価格・販売地域・税／支払情報・Paid Apps Agreementの内容                     | 有料契約同意、アプリ／教材の課金開始       |

Developer Program加入費用と、アプリ／教材を有料販売する契約は別です。個人登録では法的氏名が販売者名として表示されます。加入や氏名公開は本人が確認します。[Apple: Program enrollment](https://developer.apple.com/help/account/membership/program-enrollment/)

有料アプリやIAPを提供する場合はAccount HolderによるPaid Apps Agreementへの同意が必要です。同意・銀行／税情報の入力を代行実行しません。デジタル教材の販売方式は地域と提出時の規則を確認して別計画にし、初版へ無断で外部決済導線を追加しません。[Apple: Agreements](https://developer.apple.com/help/app-store-connect/manage-agreements/sign-and-update-agreements/)
